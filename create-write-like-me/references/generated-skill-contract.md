# Generated skill contract

Use this contract while building and validating the personalized skill. Adapt file names and metadata to the harness.

## Universal invariants

Every generated skill must:

- preserve facts, quotations, commitments, constraints, and degrees of certainty;
- add no unsupported experience, cause, promise, or conclusion;
- retain source wording when a change has no identifiable benefit;
- keep personal style subordinate to the reader, purpose, and risk;
- distinguish personal preferences from universal safeguards.

## Minimal architecture

Require the platform's primary skill file. Add only resources justified by progressive disclosure:

- a shared voice profile when details would bury the main steps;
- one language profile only when that language has distinct rules;
- a register file only when exact vocabulary or translations matter;
- metadata only when the harness supports and benefits from it;
- scripts only for repeated deterministic work that prose cannot perform reliably.

Keep each meaning in one place. Point to a reference exactly where its branch needs it. Bundle short canonical transformations, not the user's corpus.

## Invocation

Default to model discovery plus explicit user invocation. Write a compact trigger description covering genuinely distinct branches. If the user chooses explicit-only invocation, express that choice using the current platform's supported mechanism rather than assuming a particular metadata file.

## Writing branches

Encode every accepted requested or dynamically discovered branch:

- **Creation:** shape supplied ideas in the personal voice.
- **Rewrite:** preserve invariants while changing ideas, structure, rhythm, and words to the validated depth.
- **Translation:** write naturally in the target language using its profile instead of translating mannerisms literally.
- **Adaptation:** change format or audience while retaining the voice signals that fit the new context.

Use canonical before-and-after pairs as calibration anchors. Apply each pair as a contextual, transferable transformation.

## Build rejection rules

Audit these rules by ID and reject a build when any is true:

- `C1`: a confirmed decision has no executable home;
- `C2`: the same rule appears in multiple files;
- `C3`: a must-use reference has a vague pointer;
- `C4`: examples dominate the instructions or leak a full source corpus;
- `C5`: style rules from one language are copied into another without validation;
- `C6`: a rewrite test changes mainly synonyms when the validated profile calls for deeper work;
- `C7`: any provisional rule is unmarked or lacks an approved passing test;
- `C8`: a translation direction lacks its own rule or an explicitly validated shared rule.

Use gates `G2`–`G4` in [the run ledgers](run-ledgers.md) for validation, blind-test approval, and delivery. Do not duplicate their criteria here.
